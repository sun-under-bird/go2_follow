# 本轮跟随优化与验收：2026-10-05

当前结果：开阔跟随达到约 0.5 m/s，长横向障碍和直角盲弯通过本轮流畅性门槛；连续交错障碍完成绕行，但仍有明显低速和掉队。**还没有整体达到“像真狗一样流畅跟随避障”。**

## 1. 当前方案与修改原因

默认身份为 `rate / annulus / cone / steady / process`，分别对应角速度执行、跟随距离区域、扇区观察、单调时钟唤醒、独立搜索进程。

链路为：UWB 世界目标及有效性 → 前视深度静态历史滚动地图 → Dijkstra 搜索可达跟随区域或已知通道进展 → 缺少通道时进行有反馈的区域观察 → Nav2 MPPI DiffDrive 跟踪 → 加速度/加速度变化率限制和实际制动轨迹检查 → 底盘命令。

| 本轮修改 | 为什么 |
|---|---|
| 搜索以 spawn 独立进程读取地图快照，启动前预热 | 将搜索与物理、渲染、ROS 控制线程的 Python 调度隔开；不序列化节点或控制锁 |
| 只有真正接入的搜索结果提交 previous/side | 陈旧、冲突或排除的候选不应改变下一轮终点及绕行偏好 |
| 移动目标的跟随区域加入参考不足软代价 | 人仍在走时，当前位置可能因路程为零成为最便宜终点，导致 FollowPath 反复结束 |
| 参考供给只计算沿目标运动方向的进展 | 单纯偏好更长路径曾触发“人刚转弯，狗反向绕圈”的已有反例；该失败没有放宽测试门槛 |
| 人停在距离带内时允许保持已知安全站位 | 部分人与狗之间的视线未知，不应迫使狗继续绕圈；明确隔墙证据仍交给绕行规划 |
| 保持前检查残余运动，撤销 MPPI 跟踪 | 原地保持也必须检查实际停车轨迹；不能继续接收上一移动动作的候选命令 |
| 报告记录搜索进程 PID、CPU/墙钟时间与五项运行身份 | 区分算法计算、等待和不同模式，并核验本轮搜索进程退出 |

参考期望覆盖 2.4 s MPPI 窗口和 0.4 s 搜索间隔，0.5 m/s 时约 1.4 m。它只是安全距离区域内的软偏好；短通道仍可使用，从未观察的区域仍不可行驶。

碰撞包络、未知区域约束、制动检查和输入健康门槛没有放宽。角速度仍限制为 ±0.4 rad/s。本轮不处理低速死区和起步响应。

独立进程的 trail/camera 试验另存 `navigation-process-search-20261005-consecutive`，仍未完成绕行，未替换默认方案。采样最大搜索墙钟时间约 150.53 ms、CPU 150.46 ms，观察序列达到 13；此前线程诊断出现 3–4 s 墙钟时间、约 0.64–0.84 s CPU，观察序列为零。不同轨迹导致地图任务不同，这不是严格相同输入性能对照，但已能验证新进程可及时生成并接入观察任务。不能据此宣布相机观察方案通过。

## 3. 为什么还不能靠放宽安全参数解决

新连续障碍正式采样中 `EXECUTION_LIMITED` 为零，低速主要出现在 MPPI 的参考跟踪及观察动作。20–35 s 区间实际 vx 约 0.04–0.06 m/s，之后绕过第二障碍才恢复移动。执行层的速度裁剪不是本次主要原因；未知区和包络仍会影响规划能选择的通道。

轨迹显示狗绕第二障碍上侧，人走下侧，产生较长绕行。因此下一步应围绕下一段可通行包络选择真正有用的视点，并保持可执行路线连续性，不能只奖励未知面积或提高命令上限。

当前 DiffDrive 只发 vx/wz；0.4 rad/s 转过 90° 理论需要约 3.9 s。已有锁定模型的 `execution-rate-20261004` 能力基准中，原地请求 +0.8 rad/s，末段实测约 +0.443 rad/s，模型输入饱和占比 99.75%；负向约 −0.621 rad/s。没有依据把上限简单翻倍。

五项姿态与停车检查通过，完整速度跟踪未通过。这只描述仿真模型，不代表 Go2 实机 Sport 接口的横移或倒退能力。**本轮没有切换 Omni；切换前须匹配可验证的三轴执行模型和碰撞轨迹。**
