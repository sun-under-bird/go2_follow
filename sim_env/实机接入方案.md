## 1. 最终链路与参数归属

```text
原 uwb_target_adapter_node ── /uwb/target_point ─────────────┐
原 stereo_obstacle_projector_node ─ /local_grid_obstacle ───┤
                                 └ /stereo/depth_debug ────┤
原相机 ─ CameraInfo + 真实安装 TF ───────────────────────────┤
真实里程计 ─ /odom + 采集时刻 TF ───────────────────────────┘
                     ↓ 真实消息检查、转换与同帧配对
        原 UWB 估计/历史 + 原深度滚动地图（叠加原节点障碍点）
                     ↓ 原位置/朝向 Dijkstra 搜索
              原 Nav2 MPPI + 原自定义 Critic
                     ↓ 原平滑、限速及矩形停车检查
              /cmd_vel（geometry_msgs/Twist）
                     ↓ 用户已有底盘桥
                   真实底盘
```

实机入口固定采用当前仿真默认的 `trail / camera / steady / process`，使用真实 ROS 时间（`use_sim_time=false`）。不经过 MuJoCo、ONNX 步态或仿真速度校准；实际底盘自行执行速度。

| 配置/代码 | 在这条链路中的用途 |
|---|---|
| [navigation_config.py](follow_demo/navigation_config.py) | 保留仿真跟随、搜索、包络及制动参数 |
| [mppi_runtime.py](follow_demo/mppi_runtime.py) | 保留 Nav2 MPPI 优化参数，仅替换时间、话题和参考帧 |
| [uwb_follow_only.yaml](../src/go2_uwb_local_follow/config/uwb_follow_only.yaml) | 仅使用其中 UWB 适配节点的原始输入、外参和目标点输出配置 |
| [stereo_obstacle_cloud.yaml](../src/go2_uwb_local_follow/config/stereo_obstacle_cloud.yaml) | 继续用于原双目感知节点的投影和过滤 |
| [local_velocity_planner.yaml](../src/go2_uwb_local_follow/config/local_velocity_planner.yaml) | 这条链路不加载旧规划控制器参数 |

MPPI 基线仍为 `batch_size=800`、`iteration_count=1`、`model_dt=0.05 s`、48 步（2.4 s）、`DiffDrive`；最高线速度 `0.8 m/s`、角速度 `1 rad/s`。机身矩形 `0.70 × 0.32 m`，制动减速度假设 `0.45 m/s²`。跟随与观察两套 Critic 配置均与原仿真相同。这些是基线假设，实际机身包络、制动和执行延迟仍须测量后核对。

## 2. 为什么还需要同源深度

`/local_grid_obstacle` 只包含障碍命中点。没有点的区域可能是遮挡或测量失败，不能直接当作自由空间。原仿真策略依靠完整深度及采集时刻 TF 建立可通行区域，因此实机入口同时消费原投影节点已经支持的 `/stereo/depth_debug`。

开启 `publish_debug_depth:=true` 后，原节点从同一视差帧输出米制 `32FC1` 深度及障碍点云，两者保留同一原始时间戳。接入层只转发时间戳完全相同的深度/云；点云只增加障碍证据，自由空间仍由原深度算法决定。丢失其中一路、无效深度、过期帧或缺失 TF 都不能刷新地图健康时间。仅发布障碍点云不足以运行当前入口。

本入口暂不消费 `/local_depth_observation`（它是含射线字段的 `PointCloud2`），没有引入另一套射线建图策略。

## 3. 输入及坐标要求

| 默认输入 | 消息类型 | 要求 |
|---|---|---|
| `/odom` | `nav_msgs/msg/Odometry` | `header.frame_id=odom`，`child_frame_id=base_footprint`；真实采集时间、有效姿态和实测 twist |
| `/uwb/target_point` | `geometry_msgs/msg/PointStamped` | 原 UWB 适配器输出；若不是配置的机身系，则通过采集时刻 TF 转换 |
| `/local_grid_obstacle` | `sensor_msgs/msg/PointCloud2` | 原投影节点的 XYZ 云，包含原始采集时间和真实参考帧 |
| `/stereo/depth_debug` | `sensor_msgs/msg/Image` | 原投影节点的同帧校正深度；真实光学 frame；无效值保持无效 |
| `/camera/camera/infra1/camera_info` | `sensor_msgs/msg/CameraInfo` | 与深度尺寸、光学 frame 和校正后内参一致 |
| `/tf`、`/tf_static` | TF | 能查询 `odom ← depth optical` 和 `odom ← cloud frame` 在采集时刻的变换 |

里程计与 TF 必须使用相同的位姿来源。默认平地地图把地面视为 `odom` 的 `z=0`；相机高度、俯仰和机身外参须反映实际安装。仅有 `/odom` 消息不会自动建立 TF。不得用重写 `frame_id` 或刷新时间戳代替真实变换和时间同步。

点云对应的 TF 稍晚到达时，接入层保留最多 16 帧等待原采集时刻变换，保持时间戳不变。深度和地图仍按原 0.9 s 新鲜度门槛拒绝过期结果。

默认机身帧可通过 `--base-frame` 修改；默认里程计帧可通过 `--odom-frame` 修改。`--depth-frame` 必填，从真实深度和 CameraInfo 的 header 读取。若 `/odom` 的 child 是 `base_link`，就配置该帧并提供与 UWB、相机及云的真实 TF，不能只改里程计消息标签。

接入层也支持 `16UC1`：默认每单位 `0.001 m`，驱动定义不同时用 `--integer-depth-scale` 设置。当前原节点输出 `32FC1` 米制深度，不使用这个整数比例。[ROS 深度图单位约定](https://github.com/ros-infrastructure/rep/blob/master/rep-0118.rst)；[ROS 机身及里程计参考帧约定](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)。

## 4. 实机上如何启动

以下命令在 **Ubuntu Bash** 中执行。`GO2_FOLLOW_REPO` 改为实机上本仓库的绝对路径。本机 WSL 对应 `/mnt/d/work/go2_follow`。

先按原方式启动相机、UWB 原始驱动及真实里程计。UWB 目标点适配器若已运行，保留该节点；否则单独运行适配器：

```bash
export GO2_FOLLOW_REPO=/mnt/d/work/go2_follow
source /opt/ros/humble/setup.bash
# 先 source 实机现有 ROS 工作区的 install/setup.bash。
ros2 run go2_uwb_local_follow uwb_target_adapter_node --ros-args \
  --params-file "$GO2_FOLLOW_REPO/src/go2_uwb_local_follow/config/uwb_follow_only.yaml"
```

另一个终端启动原双目感知链。若已运行投影节点，停止该实例后用此参数重新启动，避免重复发布：

```bash
source /opt/ros/humble/setup.bash
# source 实机现有 ROS 工作区。
ros2 launch go2_uwb_local_follow stereo_obstacle_cloud.launch.py \
  publish_debug_depth:=true
```

保留传感器/目标适配节点和用户已有底盘桥；关闭旧 `uwb_follow_controller_node`、`local_velocity_planner_node` 等旧速度规划发布节点，让新入口成为交给底盘桥的唯一速度来源。不要用包含旧跟随控制器的 `uwb_follow_only.launch.py` 或 `local_follow.launch.py` 代替上面的单节点启动。

读取实际输入的 header：

```bash
ros2 topic echo /odom --once
ros2 topic echo /stereo/depth_debug --field header --once
ros2 topic echo /camera/camera/infra1/camera_info --field header --once
```

第三个终端启动新入口。下例 `camera_infra1_optical_frame` 是示例，必须替换成刚才读到的实际光学帧：

```bash
export GO2_FOLLOW_REPO=/mnt/d/work/go2_follow
source /opt/ros/humble/setup.bash
# source 实机现有 ROS 工作区；保留它的 ROS_DOMAIN_ID 和 DDS 网络配置。
source "$GO2_FOLLOW_REPO/sim_env/follow_demo/hardware_setup.bash"
export PYTHONPATH="$GO2_FOLLOW_REPO/sim_env:${PYTHONPATH:-}"
python -m follow_demo.hardware_runtime \
  --odom-topic /odom \
  --odom-frame odom \
  --base-frame base_footprint \
  --cmd-vel-topic /cmd_vel \
  --depth-frame camera_infra1_optical_frame
```

`--cmd-vel-topic /cmd_vel` 是默认值，显式写出便于核对现有底盘桥。发布的 `linear.x` 为机身前向速度（m/s），`angular.z` 为偏航角速度（rad/s）；其余分量为零。需要只看算法输出、不交给底盘桥时，改成 `--cmd-vel-topic /go2_follow/cmd_vel_candidate` 即为影子运行。该切换不改变跟随、地图、搜索、MPPI 或最终停车检查。

所有外部输入话题均可用对应的 `--*-topic` 参数覆盖，完整参数见 `python -m follow_demo.hardware_runtime --help`。输入检查后转发到 `/go2_follow/input/*`，保留采集时间。可靠转发 `/odom` 以兼容 Humble Nav2 的里程计订阅。

按 `Ctrl+C` 结束入口，入口会回收自己启动的 Nav2 子进程；也可用 `--duration 30` 限定运行 30 秒。

**实机不要 source 仿真用的 `follow_demo/setup.bash`**：它会切换到固定 DDS 域和回环网卡。新 `hardware_setup.bash` 保留调用者的域和网卡。原算法内部仍用 `/follow_demo/*` 与 `/go2_follow_mppi/*`，同一 DDS 域只能启动一套本策略。

运行依赖是 ROS 2 Humble Nav2/MPPI、NumPy、OpenCV、PyYAML 和本仓库两个原生 Critic 插件。本机 WSL 已有这些依赖。实机若为 ARM，必须在实机上编译 `sim_env/native/go2_follow_mppi_critics`，不可拷贝 WSL 的 x86 `.so`：

```bash
source /opt/ros/humble/setup.bash
cmake -S "$GO2_FOLLOW_REPO/sim_env/native/go2_follow_mppi_critics" \
  -B "$HOME/go2_sim/native/build" \
  -DCMAKE_INSTALL_PREFIX="$HOME/go2_sim/follow_native" \
  -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build "$HOME/go2_sim/native/build" --parallel 2
cmake --install "$HOME/go2_sim/native/build"
```

编译依赖及基础环境见 [异机从零复现指南](异机从零复现指南.md)。新的 Python 硬件入口自身不导入 MuJoCo、ONNX Runtime 或 `unitree_go` 消息。

## 5. 自动运行与停止条件

现有底盘桥直接订阅 `/cmd_vel` 即可。启动入口后自动处理传感器数据，查看：

```bash
ros2 topic echo /go2_follow/control_status
ros2 topic echo /cmd_vel
```

实机入口没有订阅操作状态话题，也不会等待操作者的 enabled、ready 或净空确认。每次启动为新的内部数据会话；重建地图/历史可结束后重启入口。仿真网页的操作按钮和心跳逻辑仍保留在仿真入口。

仅取消人工启动门槛，不自动填充原先人工确认的 1.2 m 自由区域。起点和路径的可行驶空间必须来自真实深度观测；未知空间仍禁行。因此真实数据存在但诊断为 `FOOTPRINT_UNKNOWN` 时，应核对起点是否在真实深度视野内，而不是再发送确认消息。地图诊断中的 `confirmed=false` 在实机自动模式下是正常状态，不再阻止运行。

保留原门槛：UWB 目标最大年龄 0.45 s，控制里程计最大年龄 0.2 s，深度地图最大年龄 0.9 s。无效值、缺失采集时刻 TF、同帧深度/云不匹配、MPPI 候选过期或矩形停车检查未通过时，仍会停止或限速；输入恢复后由原控制条件决定能否继续。状态中的 `operation_mode=automatic`、`start_confirmation_required=false` 表示当前实机运行方式。

停止运行使用 `Ctrl+C`，现有底盘桥继续负责其真实硬件停止/超时机制。不要把 `/follow_demo/mppi_cmd` 直接交给底盘桥：它是内部优化候选，尚未经过最终执行检查。
